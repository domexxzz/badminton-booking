select

   where table_schema = 'public'
     and table_name in ('party_singles_queue', 'party_singles_match_board')) as tables_found,
  (select count(*) from pg_proc p join pg_namespace n on n.oid = p.pronamespace

| ผลที่ได้ | แปลว่า | ต้องทำ |

## ลำดับการรัน migration

**กฎเหล็ก: รัน SQL ให้ครบก่อน แล้วค่อย merge** ไม่ใช่ merge ก่อนแล้วค่อยรัน
(ที่เพิ่งเกิดกับ 0028 คือทำกลับด้าน)

### ปลอดภัยไหมถ้ารัน SQL ก่อน ทั้งที่โค้ดเก่ายังอยู่บนเว็บ

**ปลอดภัย และทดสอบแล้ว** `0031` มีการ drop แล้วสร้างใหม่สามฟังก์ชันที่โค้ดบน
production เรียกอยู่ (`create_party_booking`, `join_party`, `my_party_entries`)
ผมจึงรันฐานข้อมูลจำลองที่ใส่ migration ใหม่ครบ แล้วเรียกฟังก์ชันเหล่านั้น**แบบเดียวกับที่
โค้ดบนเว็บตอนนี้เรียก** ผลคือเรียกได้ครบทุกตัว:

- `create_party_booking` ด้วยพารามิเตอร์เดิม 6 ตัว → ได้ห้องสาธารณะแบบจัดอันดับโดยอัตโนมัติ
- `join_party` ด้วยพารามิเตอร์เดิม 4 ตัว → เข้าห้องสาธารณะได้ ไม่ต้องใช้รหัส
- `my_party_entries` → คอลัมน์เดิมครบ (มีคอลัมน์ใหม่เพิ่มมา ซึ่งโค้ดเก่าไม่สนใจ)

และต่อ websocket ของ Supabase ต้องแยกไปทำอีก PR ที่ทดสอบกับเว็บจริง)

### 2. เครื่องมือ sandbox — ทดสอบได้โดยไม่แตะฐานข้อมูลจริง

ร้านไม่มีฐานข้อมูลสำหรับทดสอบ และ local dev ชี้ไปฐานข้อมูลจริง ผมจึงทำสองอย่าง

- **`npm run sandbox`** — Postgres ของจริงที่เกิดในโปรแกรม รัน migration ครบทุกไฟล์
  แล้วจำลองคืนก๊วนให้ดู **ไม่อ่าน `.env` ไม่ต่อเน็ต รันตอนลูกค้าจองอยู่ได้**
- **หน้า `/sandbox/*`** — วาดหน้าจอจากข้อมูลสมมติ เพื่อดูที่ขนาดมือถือ 390px
  **เป็น 404 บน production** (ทดสอบแล้วด้วย `next start` จริง)

ย้ายรายชื่อ migration ไปอ่านจากโฟลเดอร์แทนที่จะพิมพ์ซ้ำสองที่ — รายชื่อที่ค้างเก่า
คือสาเหตุที่ migration พังหลุดไปใน PR #23

### 3. ระบบจับคู่แบบเกมออนไลน์

- **แต้ม Elo เริ่มที่ 1000 ติดตัวข้ามคืนก๊วน** ชนะคนแต้มสูงกว่าได้เยอะ ชนะคนแต้มต่ำกว่าได้น้อย
  แต้มที่ผู้ชนะได้ = ที่ผู้แพ้เสียพอดี
- **ตัวจับคู่**: คนที่ลงสนามน้อยที่สุดได้เล่นก่อน → แล้วจึงดูฝีมือใกล้เคียง → ใครรอนานเกิน
  จะถูกดันขึ้นก่อนทุกเงื่อนไข
- **ชนะติดกันครบ 3 เกมต้องพัก** (หัวห้องปรับ 2/3/5 ได้) · **ไม่เจอคู่เดิมซ้ำติดกัน**
- โชว์แต้มที่จะได้ก่อนกดเลือกผู้ชนะ

**ผลจากคืนจำลอง 8 คน 24 เกม:** ทุกคนได้ลง 5–7 เกม ต่างกันไม่เกิน 2 เกม · ไม่มีใครครองสนาม
เกิน 3 เกมติด · ไม่มีการเจอคู่เดิมซ้ำติดกันเลย · ตารางอันดับเรียงตามฝีมือจริง

### 5. ห้องก๊วนรุ่นใหม่

สร้างห้องเลือกได้: **เดี่ยว/คู่** · **สาธารณะ/ส่วนตัว** · **จัดอันดับ/ชิลๆ**
ห้องส่วนตัวได้รหัส 6 ตัว (ไม่มี `0 O 1 I L` เพื่อไม่ให้อ่านสับสน) แชร์เป็นข้อความ ลิงก์ หรือ QR
สแกนแล้วเข้าได้เลยไม่ต้องพิมพ์รหัส

ฝั่งคนหาห้อง: แยกแท็บเดี่ยว/คู่ และจัดอันดับ/ชิลๆ · ใส่รหัสเข้าห้องส่วนตัว ·
**auto join** ที่เลือกห้องที่คนใกล้เต็มที่สุดก่อน (ไม่สุ่มล้วน เพราะสุ่มล้วนจะได้คืนที่มี
สี่ห้อง ห้องละสองคน แล้วไม่มีใครได้เล่น)

**หัวห้องตั้งผู้ดูแลและโอนหัวห้องได้** ผู้ดูแลกดผลการแข่งและตั้งกติกาได้ แต่โอนหัวห้องต่อ
ไม่ได้ และเอาผู้ดูแลด้วยกันออกไม่ได้ — บังคับในฐานข้อมูล ไม่ใช่แค่ซ่อนปุ่ม

### 6. คอมมูนิตี้ พร้อมระบบดูแลเนื้อหา

โพสต์ คอมเมนต์ ถูกใจ และปุ่มรายงานทุกชิ้น เข้าคิวให้แอดมินที่ `/admin/community`

- **ไม่มีอะไรถูกลบจริง** — โพสต์ที่เจ้าของลบหรือแอดมินซ่อน ยังเก็บข้อความไว้พร้อมเหตุผล
  หายจากทุกหน้าจอทันที แต่ตรวจสอบย้อนหลังได้ และซ่อนแล้วเอากลับขึ้นได้
- **หนึ่งคนรายงานของชิ้นเดียวกันได้ครั้งเดียว** ปั่นคิวไม่ได้
- **จำกัดความถี่ในฐานข้อมูล** 10 โพสต์/ชม. 30 คอมเมนต์/ชม. เลี่ยงด้วยการยิง API ตรงไม่ได้
- **สวิตช์ปิดรับโพสต์ชั่วคราว** กดจากหน้าแอดมิน ไม่ต้อง deploy

กฎของโปรเจคตั้งแต่ migration 0020 คือ **บอร์ดสาธารณะห้ามมี user id**
ตารางอันดับและคอมมูนิตี้จึงใช้ `profiles.public_player_id` ซึ่งเป็น uuid ใหม่ที่ไม่เกี่ยวกับ

ไปหาบัญชีไม่ได้ — sandbox เช็กว่าไม่มีคีย์ไหนตรงกับ `auth.users.id` เลยสักแถว

## สิ่งที่โดมต้องตัดสินใจ

### 1. ตารางอันดับ — ขึ้นชื่ออัตโนมัติ หรือต้องขอขึ้นเอง

ตอนนี้ตั้งเป็น **ขึ้นชื่ออัตโนมัติ แล้วใครไม่อยากขึ้นค่อยกดออก** เพราะถ้าต้องขอขึ้นเอง
ตารางจะว่างตั้งแต่วันแรกจนไม่มีใครอยากใช้

ตารางแสดง**ชื่อกับรูปโปรไฟล์ให้คนที่ล็อกอินเห็น** (ไม่เปิดให้คนทั่วไป) สองอย่างนี้ห้องก๊วน
ก็แสดงอยู่แล้ว แต่**ตารางอันดับเก็บไว้ต่อหลังคืนนั้นจบ ซึ่งต่างกันในเชิงหลักการ**

**ถ้าอยากเปลี่ยน:** แก้ `0030_player_leaderboard.sql` บรรทัดที่เขียนว่า
`show_on_leaderboard boolean not null default true` เปลี่ยน `true` เป็น `false`
**ก่อนรัน SQL** คำเดียว ที่เหลือทำงานเหมือนเดิมหมด

### 2. คอมมูนิตี้ — ใครดูแลคิวรายงาน และภายในกี่ชั่วโมง

ระบบพร้อมแล้ว แต่**ต้องมีคนเปิดดู `/admin/community`** ถ้าสัปดาห์ไหนไม่มีคนดูแล
**กดปิดรับโพสต์ไว้ก่อนได้** จากหน้าแอดมิน ไม่ต้อง deploy คนยังอ่านของเดิมได้

ถ้ายังไม่พร้อมเปิดเลย: **ไม่ต้องรัน `0032`** ส่วนอื่นทั้งหมดใช้งานได้ตามปกติ
(หน้า `/community` จะพัง ต้องเอาลิงก์ออกจากหน้าคิวก๊วนและหน้าของฉันก่อน — แจ้งได้ เดี๋ยวแก้ให้)

### 3. การโพสต์รูป

ผมเตรียม storage bucket และสิทธิ์ไว้แล้ว แต่**ยังไม่ได้ต่อปุ่มอัปโหลดรูปใน UI**
ตอนนี้โพสต์ได้เฉพาะข้อความ เพราะรูปคือจุดเสี่ยงสูงสุด (ไม่มีการตรวจอัตโนมัติ)
อยากเปิดเมื่อไหร่บอกได้

### 4. ราคาสนาม ฿130 หรือ ฿150

ฐานข้อมูลใช้ `courts.price_per_hour` = **฿130** และทุกหน้าอ่านจากตรงนั้น
ส่วนเลข 150 ใน `config.ts` **ไม่มีโค้ดไหนอ่านเลย** ผมใส่คอมเมนต์กำกับไว้แล้วว่าฐานข้อมูลเป็นตัวจริง
ถ้าอยากให้ลบเลขนั้นทิ้งเลย บอกได้

### 5. เรื่องที่ควรคุยกับทีม

**`main` ไม่มี branch protection และไม่มี CI** — merge เข้า main = deploy ทันที
โดยไม่มีอะไรรันเทสต์ให้เลย เรื่อง 0028 ที่เพิ่งเกิดคือตัวอย่างว่าทำไมมันเสี่ยง
ควรเปิด branch protection (ต้องมี PR + อนุมัติ) และเพิ่ม GitHub Action ที่รัน
`npm test` กับ `npm run test:db` ทุก PR

เทสต์ใหม่ทุกชุด **ทดลองทำโค้ดพังกลับคืนแล้วยืนยันว่าเทสต์แดงจริง** ตามกฎใน `AGENTS.md`

ดูหน้าจอจริงที่ **390px** แล้ว: ห้องก๊วนเดี่ยว/คู่ · ตารางอันดับ · สถิติตัวเอง · คอมมูนิตี้ ·
คิวรายงานแอดมิน · คู่มือ

### ยังไม่ได้ตรวจ

1. **Realtime ข้ามเครื่อง** — ยังไม่ได้พิสูจน์ว่าหัวห้องกดผลแล้วมือถือคนอื่นอัปเดตเองจริง
   ต้องมีฐานข้อมูลจริงกับคนสองเครื่อง
2. **การ์ดแชร์รหัส/QR, หน้าจัดการห้อง, หน้าหาห้อง** — เขียนและ typecheck แล้ว
   แต่ยังไม่ได้เห็นบนจอจริง เพราะต้องมีห้องจริง (ทำหน้า sandbox ให้ดูได้ถ้าต้องการ)
3. **รูปโปรไฟล์จาก LINE/Google บนตารางอันดับ** — ข้อมูลสมมติใช้ตัวอักษรย่อแทนรูป
4. **ไม่มี dark mode** — `globals.css` ตั้ง `color-scheme: light` ตายตัว ไม่มีชุดสีมืด
   กฎใน `AGENTS.md` ที่ให้ "เช็ค light และ dark" ทำตามไม่ได้จริง เพราะไม่มี dark ให้เช็ค
   (มี `@media (prefers-color-scheme: dark)` ค้างอยู่ 4 ก้อน แต่งเฉพาะการ์ดหน้า review
   ของแอดมิน ซึ่งจะทำให้การ์ดนั้นสีเข้มคนเดียวบนมือถือที่เปิด dark — ของเดิม ไม่ใช่จากงานรอบนี้)

## คำสั่งที่ใช้บ่อย

```bash
npm run sandbox    # จำลองคืนก๊วนทั้งคืน ไม่แตะฐานข้อมูลจริง
npm run test:db    # ตรวจกฎในฐานข้อมูลทั้งหมด
npm test           # เทสต์โค้ด
npm run build      # ตรวจว่าขึ้นเว็บได้
npm run dev        # แล้วเปิด /sandbox/party, /sandbox/leaderboard, /sandbox/community
```

หน้า `/sandbox/*` เปิดได้เฉพาะตอน `npm run dev` เท่านั้น บน production เป็น 404
